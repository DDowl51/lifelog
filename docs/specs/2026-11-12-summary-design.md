## 3. 升到复杂档（13a）

**为什么要升**：生成摘要要写数据库，而常驻进程是唯一的写者。`lifelog summarize`（systemd timer 每天调用，用户也可以手动调）跑在只读的命令行进程里，必须把这次调用交给常驻进程。

**做法：kernel 提供「同名契约的远程代理」**，按规范的复杂档：代理和传输属于 kernel，组件和契约一行不改。

- `contract!` 宏为每个请求契约多生成两样东西：
  - **分派**：按方法名 + JSON 参数调用一个实现，返回 JSON 结果；
  - **代理**：实现同一个 trait，把每次调用编码成 `{契约, 方法, 参数}` 发给一个传输，再把结果解码回来。
  契约本来就只传纯数据（原则 5，编译器检查过），所以这一步不需要改任何契约。
- **导出**：常驻进程的启动器在配置里声明要导出哪些契约；kernel 在 `$XDG_RUNTIME_DIR/lifelog/lifelogd.sock` 上监听，按行收 JSON 请求、分派给进程里的提供者、按行回结果。
- **导入**：命令行进程声明要从那个 socket 导入哪些契约；kernel 把代理当成一个提供者放进来。使用方 `resolve` 到的句柄和进程内的没有区别。
- 协议：按行分隔的 JSON；握手交换契约名和版本号，主版本不一致拒绝连接。常驻进程不在、连接断了：调用返回 `unavailable`，提示「先启动 lifelogd」。
- 只导出写命令需要的契约（第一个是 `Summarize`）。查询照旧在命令行进程里直接读数据库，不绕常驻进程。
- 以后的 `lifelog reprocess`（用新规则重新归类旧记录）走同一条路，只是多导出一个契约。

**代价**：kernel 第一次有 IO（一个 Unix socket）。规范写的是「IPC 是微内核的本职」，这一步验证它。kernel 的外部依赖仍然只有 tokio。

## 4. 每日摘要（13b）

### 4.1 组件

| 组件 | 类别 | 提供 | 需要 |
|---|---|---|---|
| `llm-openai-compat` | 系统服务 | `Llm`：`complete(消息们, 选项) → 文本` | `Log` |
| `files-std` | 系统服务 | `Files`：在配置的根目录下读写、列出文本文件 | |
| `documents` | 应用功能 | `DocumentWrite`、`DocumentRead`：长文本（摘要、以后的笔记），表 `documents_*` | `Sql`、`Migrations`、`Clock` |
| `summary` | 应用功能 | `Summarize`：`summarize(日期, 是否强制) → 结果` | `Memory`、`Llm`、`Files`、`DocumentWrite`、`Clock`、`Log` |
| `search` | 应用功能 | 加：文档也进全文索引，检索结果里出现「摘要」 | 可选 `DocumentRead` |

契约里不出现 OpenAI、模型名；`Llm` 的另一个实现（本机模型、别的服务商）是另一个组件。

### 4.2 流程

1. **预聚合**（纯逻辑）：从 `Memory` 取这一天的按项目、时间线、命令、网页，压成一份结构化的「这一天」文本：每个项目的时长和主要窗口标题、按时间的几大段、命令按项目的前若干条、网页标题前若干个（只给标题和域名，不给完整网址）。有长度上限。
2. **生成**：固定的提示词 + 这份文本 → `Llm`。提示词是配置（可以换成一个文件）。输出 Markdown：概览、按项目、时间线要点、未完成 / 明天继续。
3. **保存**：写 `~/lifelog/daily/2026-11-12.md`（根目录可配），同时存进 `documents`（种类 `summary_daily`）。
4. **手改**：文件里记下生成时的内容哈希。再次生成时，文件被手改过就不覆盖（除非 `--force`）；手改过的文件由 `notes`（阶段 15）同步回文档库。

### 4.3 什么时候生成

- `lifelog summarize [<日期>] [--force]`：默认昨天。
- systemd timer：每天 04:30（日界之后）运行 `lifelog summarize`，`Persistent=true`，关机错过的开机后补。错过好几天时补最近 N 天（配置）。
- 模型接口不可用：命令以 69 退出，systemd 记失败，下次再补。

### 4.4 隐私

发给云端的就是 §4.2 第 1 步那份文本。规则：

- `query` 的 `hidden_sources` 本来就生效；`summary` 另有自己的 `hidden_sources`（默认空，见待确认 Q3）。
- 入库时已经脱敏过（密钥、密码管理器、隐私窗口）；完整网址不发。
- `lifelog summarize --dry-run` 打印要发出去的那份文本，不调用模型。

### 4.5 密钥

API key 不写进配置文件：配置写 `api_key_cmd = "pass show …"`（启动库已经支持 `*_cmd`），或者读环境变量。

## 5. 向量检索（14）

- `Embedder` 系统服务：`embed(文本们) → 向量们`。第一个实现见待确认 Q2。
- `vectors` 应用功能：只给**文档**（摘要、笔记）算向量，不给窗口标题和命令（短文本收益小，量也大）。文档按段切块，每块一个向量，存在自己的表里；数量是几百到几千，直接逐个算余弦，不装向量扩展。
- `search`：有 `VectorSearch` 时，查询同时走全文和向量，用 RRF 合并；没有时照旧。

## 6. 笔记导入（15）

- `notes` 应用功能：定时扫描配置的目录（默认包括摘要目录），Markdown 文件按内容哈希判断有没有变，变了的同步进 `documents`（种类 `note`，日记格式的文件名 `YYYY-MM-DD.md` 记下日期）；删了的从文档库删掉。
- 走 `Files` 读，不直接碰文件系统。

## 7. 待确认

| | 问题 | 我的建议 |
|---|---|---|
| Q1 | 用哪家的接口、哪个模型、key 放哪 | 你给 `base_url`、模型名；key 用 `api_key_cmd = "pass show …"`（你在用 password-store） |
| Q2 | 向量用云端的嵌入接口，还是本机模型 | 云端：和摘要同一家，不用下载模型；代价是文档内容（摘要、笔记）也会发出去 |
| Q3 | 摘要发出去的内容要不要沿用 `agent_hidden_sources` | 沿用：「不给 agent 看」和「不发给云端模型」是同一个顾虑。实现上 `summary` 读同一个配置项不合规（那是 `query` 的配置），所以给 `summary` 自己一个 `hidden_sources`，默认值写成和你现在的 `agent_hidden_sources` 一样 |
| Q4 | 笔记在哪、什么格式 | 先只管摘要目录；你的笔记目录有了再加一行配置 |
| Q5 | 升档的做法（§3：kernel 提供通用的远程代理） | 按 §3 做。另一种更省事的做法是只为 `Summarize` 手写一对「socket 服务 + 代理组件」，但那样以后每个写命令都要再写一对，也验证不了规范的复杂档 |

**决定（2026-11-12）**：Q1 用云端的 OpenAI 兼容接口；Q2 云端——选的接口没有嵌入，阶段 14 另选一家；Q3 和 agent 一样；Q4 先只管摘要目录；Q5 kernel 通用代理。

## 8. 实现中的调整

| 方面 | 设计 | 实际 | 原因 |
|---|---|---|---|
| 模型的 key | `api_key_cmd`（启动库在启动时运行） | 另加 `key_command`：第一次调用时才运行，结果记在内存里；推荐用它 | `pass` 要 gpg 解锁；启动时运行失败会让整个常驻进程起不来，窗口记录也跟着停 |
| 模型没配好 | 没写 | 常驻进程照常启动，调用时报 `unavailable` | 摘要是可选的 |
| `lifelog summarize` 登记在哪 | 没写 | 单独的小功能 `summary-cli`：只依赖 `Summarize` 和 `CliCommands`，装在命令行进程里；那里的 `Summarize` 是 `Import` 代理 | `summary` 本身要模型、文件、文档库，只能在常驻进程里；命令行的登记要在另一个进程 |
| `Memory` 在常驻进程里 | 没写 | `lifelogd` 也装上 `query` | 摘要从 `Memory` 取数据，和命令行看到的一致（含隐藏规则） |
| 文档进全文检索 | 13b | 挪到 14，和向量一起做 | 13b 先把生成、跨进程、文件、文档库走通 |
| 原料里的网页 | 「只给标题和域名」 | 时间线那一节没有标题的网页原来带着完整网址，改成只给域名 | 真机「只看不发」发现 OAuth 登录链接（带 `code_challenge`、`state`）会被发出去 |
| socket 路径太长 | 没写 | 明确报「socket 路径太长」，不再说「进程没在运行」 | Unix socket 最多 107 字节；真机验证时用的临时目录太长，报错误导人 |
| 向量用哪个模型 | 云端嵌入接口（Q2） | 改成本机：`embed-fastembed`（ONNX，`multilingual-e5-small`），第一次用时下载 | 负载不大：只给文档算，一天一篇，普通的桌面机就够 |
| 命中的阈值 | 没写 | 0.85（e5-small 的相似度挤在 0.78～0.90）：真实摘要上相关的问题 0.855～0.896，无关的 0.79～0.835 | 对着真实摘要和一段无关文字量出来的 |
| 文档怎么排 | 「有 `VectorSearch` 时混合排序」 | 文档和活动分开：活动最近的在前；文档按全文 + 向量的 RRF；结果里单独一节，带命中处的摘录 | 两类东西的找法不一样 |
| 向量检索在哪个进程 | 没写 | 常驻进程导出 `vectors.search`，命令行 / 终端界面 / MCP 用 `Import` 导入 | 查询本身也要算向量；每个命令行进程都加载几百 MB 的模型太慢（首查 3.6 秒，之后 28 毫秒） |
| 导出没有提供者的契约 | 13a：启动失败 | 跳过，调用方得到 `not_found`；`search` 收到 `not_found` 时安静地只按全文 | 按配置停用 `vectors` 是正常操作，不该让常驻进程起不来 |
| 内置隐私规则 | — | 加上命令行的密码管理器（`pass`、`gopass`，含 `$( )`、管道之后的） | 真实数据里有不少这样的命令 |
| 笔记 | 「扫描配置的目录」 | 默认扫文件根目录（`~/lifelog`）下所有 `.md`；按内容哈希判断变化；符合摘要格式的同步回那一天的摘要（同一个键） | 笔记会比较少，先不另配目录；手改的摘要因此也进检索 |

## 对规范的反馈

做的过程中发现的、架构规范里没写或不好用的地方。

1. **`start` 要分两步。** 规范里组件只有一个入口 `start(host, config)`。实际上 `start` 只能做登记：这时别的组件可能还没启动，扩展点的登记也不全。真正要调别人的事（存储服务执行各组件登记的迁移）得放在「全部登记完之后」。加了 `host.on_ready`，后台任务在全部 `on_ready` 之后才开始。
2. **事件要有归属的契约。** 规范说依赖声明在契约上，但没说事件归谁。现在每个事件属于一个契约：提供这个契约的组件才能发布，声明了需要它的组件才能订阅，kernel 在启动时检查。
3. **「kernel 不打日志」时，投递失败报给谁。** 加了一个和追踪分开的「故障」出口，由启动器提供，不管有没有开追踪都收：投递失败、后台任务崩溃、收尾超时。
4. **订阅者在处理函数里再发布事件，有界队列会卡死自己。** 投递过程中发布的事件先进一个任务内的队列，紧接着投递。规范的「事件」一节应该提醒这一点。
5. **假实现放哪。** 规范说契约包里放契约测试；假实现（假时钟、内存日志）和它对应的组件也放在契约包的 `testing` feature 后面最顺手，testkit 因此不用认识任何契约。
6. **`contract!` 宏让原则 5 由编译器检查**，值得写进规范的 Rust 落地页。代价：契约的方法只能是 `async fn x(&self, 数据…) -> Result<数据, AppError>` 这一种形状。
7. **启动失败时谁映射退出码。** 命令行服务还没启动，启动器得自己映射。把映射表放在命令行的契约包里，命令行服务和启动器共用。规范说「映射只写一次，写在边界上的系统服务里」，应改成「写在它的契约包里」。
8. **「出错在启动时失败」和命令行的可用性会冲突。** 只读的命令行进程如果因为数据库不存在就起不来，连 `--help` 都用不了。现在的做法：常驻进程启动时失败；一次性的命令行进程把系统服务的问题留到用到时再报。规范的原则 11 应该区分这两种进程。
9. **扩展点的所有者也需要假实现。** 测试「登记子命令的功能」要一个假的命令行所有者（`FakeCli`），测试数据源要一个只记录的 `ActivityWrite`（`RecordingWrite`）。规范只提到了系统服务的假实现。应用功能的契约包同样要带。
10. **每个功能三个包的手感。** 3 个功能 + 6 个系统服务 + 6 个契约 = 29 个包。`focus`、`query` 拆得很自然：纯逻辑不起任何东西就能测，`Cargo.toml` 里加 tokio 会被架构检查拦下。`activity` 的 `core` 偏薄。结论：保留；但没有纯逻辑的功能可以不建 `core`。样板主要在 `Cargo.toml`，可以接受。
11. **同一个包里可以有第二个组件。** 回放用的窗口管理器和真实的共用消息解析，放在同一个包里、不登记，由测试显式装上。规范默认「一个组件一个包」，应说明这种情况。
12. **`Sql` 契约不需要事务句柄。** 「单条只读查询 + 一批语句一个事务」到目前够用，数据应用配套里设想的 `begin() → txId` 还没用上。
13. **常驻进程配套的两条规则成立：** 「一个外部程序一个系统服务」「契约描述能力、不出现外部程序的名字」。`focus` 的代码和测试里搜不到 niri。
14. **停止顺序的细节。** 组件在 `on_stop` 里发布的事件要在它的依赖停止前投递完，所以 kernel 每停一个组件就把队列投递干净。
15. **构建脚本生成组件列表**再次验证可行（`use 包名 as _;`），并且能顺带生成「仓库里有哪些组件」，用来区分配置里「别的进程的组件」和「拼写错误」。
16. testkit 只能整体停止。想「停掉 `focus` 让它写下最后一段，再查库」做不到，那类断言放到了端到端测试里。暂不处理。

17. **真机数据才暴露的策略问题**：kakoune 把光标位置写进终端标题。规范说「策略放配置」，这次的落地是「固定规则 + 可配置的改写规则 + 合理的默认值」。值得写进常驻进程配套：采集类系统服务原样上报，清理规则属于应用功能，且要能配置。
18. **只关一个组件时，报错要能指向下一步。** 停用 `idle-wayland` 而不停用 `afk`，kernel 报「`afk` 需要 `idle@1`……或者停用 `afk`」。这条在 kernel 的通用报错里就有，不用每个组件自己写。
19. 一个功能可以没有 `contracts` 包（`afk` 不对外提供契约）。架构检查按目录认角色，少一个包不影响。

20. **界面外壳和命令行服务是同一个模式**：系统服务拥有扩展点，功能登记「描述（纯数据）+ 生成内容的请求」。第二次用这个模式只花了第一次的一半功夫，说明它可以写进规范当作通用做法：「需要把业务内容展示出去的系统服务，都用『登记描述 + 按请求生成纯数据内容』」。
21. **外壳要保持业务无关时，需要一个通用的导航参数。** 「偏移」这个抽象让外壳不认识日期也能翻页。
22. **界面的验收**：纯逻辑和 `TestBackend` 覆盖大部分；真终端用独立 socket 的 tmux 会话（`tmux -L <名>`）截屏，不碰正在用的 tmux。没有放进自动测试（依赖 tmux）。

23. **开放字段要有约定的键。** `Activity.payload` 是开放的 JSON；跨组件用到的键（`cwd`、`url`）常量放在拥有它的契约包里（`payload_keys`）。规范的原则 5 应该补一句：契约里的开放字段，跨组件读写的键在契约包里定义。
24. **「顺序是策略」也要有默认值。** 处理器顺序放配置是对的，但默认空列表会让两个处理器都启用时常驻进程起不来。现在的做法：默认值写上已知处理器的合理顺序；登记了但没列出的仍然报错。
25. **入库时加工还是查询时加工，是数据应用配套里该写的取舍。** 脱敏必须在入库时（原文不能落盘）；归类放在入库时，改了规则旧记录不会变，想重算就需要一个写命令。规范的数据应用配套没有提到这一点。
26. 扩展点的登记方也要在 `requires` 里声明扩展点；不对外提供契约的功能只需要 `core` + `component` 两个包。两条都是第三次碰到，可以写进 Rust 落地页的模板。
27. **外部程序的「游标」应该不透明。** 增量读取的进度怎么表示（行号、时间戳、还要不要等执行中的那条）只有适配那个程序的系统服务知道。契约里给一个不透明的字符串，读的一方只保存、原样传回；契约写明「可能重复给，按 id 去重」。这样换一个历史来源，读的一方不用改。
28. **可选数据源缺席时不该让常驻进程起不来。** 原则 11「出错在启动时失败」针对的是配置和装配错误；外部程序还没装属于运行时状态，适配的系统服务应照常启动，用到时报「不可用」，使用方提醒一次、定时重试。
29. **「游标不会撞」这种假设要在真实数据上验证。** 我以为纳秒时间戳不会重复，真实数据里导入的历史有上千条共用一个时间戳。教训：增量游标一律用（排序键，唯一 id），不依赖排序键唯一。已写进常驻进程配套。
30. **扩展点的方向。** 「一个消费者要所有实现」（浏览器有好几种）时，自然的想法是消费者（应用功能）拥有扩展点、各实现（系统服务）登记；但那样系统服务就依赖了应用功能，kernel 启动时拒绝。做法：加一个只做汇总的系统服务拥有扩展点，对外提供一个普通的请求契约。和 `storage-sqlite` 拥有迁移扩展点同一个形状。规范的原则 4 应该写明：扩展点必须由不低于登记方的一层拥有。
31. **系统服务之间不能共享内部代码。** 三个浏览器适配都要「复制库再打开」，R1 只允许系统服务依赖 kernel-api 和契约包，所以各写了一份（二十多行）。规模小时重复可以接受；以后重复变多，规范需要一个「不是组件的内部工具包」的角色。
32. **同一个组件在不同进程里扮演不同角色，用可选依赖表达。** `search` 在有定时器的常驻进程里建索引，在没有定时器的命令行里只检索。不用拆成两个组件，也不用进程类型的开关；装配（进程里有哪些组件）决定行为。
33. **外壳的交互能力也用「业务无关的参数」扩展。** 继翻页的「偏移」之后，输入框是第二个：页面声明要输入框和提示语，外壳负责编辑，页面只收到提交的文字。展示类系统服务的契约就这样一点点加通用能力，而不是让页面自己处理按键。
34. **给 agent 的出口是第四个「展示类系统服务」。** 命令行、终端界面、MCP 都是「系统服务拥有扩展点，功能登记描述 + 按请求生成纯数据内容」；MCP 这次连代码形状都和命令行一样（描述 + 参数 + 文本结果）。差别只在策略：给 agent 的那一份限制输出规模、多隐藏几个来源，放在功能那一侧（登记方知道哪些字段长、哪些敏感）。
35. **复杂档的代理在 Rust 里可以完全由 `contract!` 生成。** 原则 5（契约只传纯数据）由宏在编译期检查过，所以给每个契约生成「分派 + 代理」是机械的：参数按名字放进一个 JSON 对象，结果和 `AppError` 原样序列化。`Sql` 的契约测试经过代理一次通过，契约和组件一行没改——「升档只换隔离手段」成立。规范复杂档那节的「未验证」可以去掉 kernel 代理这一半；进程管理（kernel 启动进程外组件）这次没用到，仍然未验证：这里的两个进程是各自由 systemd / 用户启动的，kernel 只负责导出和连接。
36. **「导入」做成一个普通组件最省事。** 它提供那个契约，里面是代理；kernel 照常排序、校验依赖、启动，不需要为远程另开一套。由启动器登记，组件和契约都不知道它。
37. **「启动时运行 `*_cmd`」和「可选的外部依赖不拖住常驻进程」冲突。** 密钥命令（`pass`）要 gpg 解锁，启动时失败就整个进程起不来。只被可选功能用到的密钥应该在第一次用时才取。规范的 `*_cmd` 约定要补一句。
38. **被导入的契约，它的命令行登记要单独一个组件。** 提供者在另一个进程里，命令行进程里只有代理；登记子命令的那个组件只依赖契约本身（`summary-cli`）。这是「展示类系统服务的登记方」和「能力的提供方」分开的又一个例子。
39. **隐私规则要对着真实数据检查一遍。** 设计写了「只发标题和域名」，单元测试也有，但时间线那一节用的是另一份数据（没标题时是完整网址），只有在真实数据的「只看不发」里才看出来。发给外部的内容，验收里应该包括一次真实数据的预览。
40. **导出的契约要跟着「哪些组件启用了」走。** 13a 让「导出没有提供者的契约」启动失败，到 14 发现这样用户就不能按配置停用一个被导出的功能。改成跳过，调用方得到 `not_found`。规范复杂档的导出一节应该写明。
41. **重的系统服务（模型）放在长寿的进程里，其他进程经代理用。** 这是复杂档机制的第二个用途：不是为了写数据库，而是为了不在每个短命的命令行进程里加载几百 MB 的模型。
42. **「配置是文本、策略放配置」要配一份由测试保证的配置文档。** 组件一多，手写的配置说明一定会过时（README 那段已经写错了默认值）。让每个组件报出自己的默认值（`config_defaults()`），一个链接全部组件的测试对照文档，成本很低。顺带发现几个组件根本不解析配置（写什么都不报错），违反「出错尽早失败」。

## 还没做的

- **外部命令作为数据源**：让用户用一条命令输出活动，接进来当一个数据源。
